# DoozCTL Specification

**Version:** 2.0 Draft
**Status:** Canonical

---

# Vision

DoozCTL is a lightweight, vendor-neutral CLI that installs and maintains AI repository standards.

It does **not** define engineering practices.

It provides the engine that renders, installs, updates and validates repository artifacts supplied by an external Standards Package.

The repository becomes the long-term memory.

AI coding assistants become interchangeable execution engines.

---

# Philosophy

* Minimal context.
* Minimal configuration.
* Repository over conversation.
* Behavior over documentation.
* Facts over prose.
* Deterministic over magical.
* Brownfield first.
* Offline first.
* Vendor neutral.

---

# Non Goals

DoozCTL is **not**:

* an AI coding assistant
* an engineering standard
* a coding guideline
* a documentation generator
* a build system
* a package manager
* a deployment framework

---

# Core Principle

> **DoozCTL is a rendering engine for repository standards, not the author of those standards.**

Everything repository-specific comes from an external Standards Package.

---

# Standards Package

A Standards Package contains reusable repository artifacts.

Typical contents:

```text
standards/

AGENTS.md

CLAUDE.md

CODEX.md

GEMINI.md

CURSOR.md

COPILOT.md

OPENCODE.md

current-context.md

session.md

schemas/

manifest.json
```

The package is owned by the user or organization.

DoozCTL never embeds company-specific standards.

---

# Artifact Model

Everything generated by DoozCTL is an Artifact.

Every artifact has:

* source
* destination
* variables
* merge strategy
* optional schema

The engine treats every artifact identically.

It does not special-case AGENTS.md.

---

# Responsibilities

DoozCTL is responsible for:

* Repository detection
* Repository analysis
* Standards loading
* Variable resolution
* Artifact rendering
* Merge management
* Validation
* Synchronization
* Session generation
* Context generation

DoozCTL is **not** responsible for artifact contents.

---

# Engine Pipeline

```text
Repository

↓

Analyze

↓

Load Standards Package

↓

Resolve Variables

↓

Render Artifacts

↓

Merge Existing Files

↓

Validate

↓

Write
```

Every command follows this pipeline.

---

# Repository Analysis

Repository analysis produces factual metadata only.

Examples:

* language
* framework
* architecture
* package manager
* build system
* testing framework
* docker
* CI
* repository statistics

No recommendations.

No opinions.

---

# Variables

Repository analysis becomes variables available during rendering.

Example

```yaml
analysis:
    language:
    framework:
    architecture:
    tests:
```

Artifacts may reference these variables.

---

# Merge Strategies

The engine supports multiple merge strategies.

## Managed Blocks

Update managed sections only.

Preserve everything else.

---

## Replace Generated

Replace previously generated files.

---

## Overwrite

Replace entire artifact.

Used for generated state.

---

## Append

Create new immutable artifacts.

Used for session summaries.

---

# Commands

## init

Responsibilities

* Detect repository
* Analyze repository
* Load Standards Package
* Render artifacts
* Merge existing files
* Write generated artifacts
* Create manifest

---

## analyze

Update repository analysis.

Read-only.

---

## sync

Re-render all managed artifacts.

Preserve developer content.

---

## doctor

Validate repository.

Check:

* artifacts
* manifest
* managed blocks
* schemas

---

## summarize

Create new session summary.

Update current context.

---

## status

Display repository status.

---

# Generated State

DoozCTL maintains:

```text
.ai/

manifest.json

repository-analysis.json

current-context.md

sessions/
```

These files belong to the engine.

They are regenerated as required.

---

# Wrapper Files

Wrapper files are supplied by the Standards Package.

Typical wrapper:

```text
Read AGENTS.md before taking any action.

This file is generated.
```

The engine does not define wrapper contents.

---

# Constraints

The engine must be:

* deterministic
* offline capable
* cross-platform
* modular
* testable
* vendor neutral

It must never:

* overwrite unmanaged content
* fabricate repository information
* modify application code during analysis
* depend on internet connectivity
* embed company-specific guidance

---

# Acceptance Criteria

## init

* Repository detected.
* Standards Package loaded.
* Artifacts rendered.
* Existing managed files merged.
* Manifest created.

---

## analyze

* Repository facts updated.
* No application files modified.

---

## sync

* Managed artifacts updated.
* Developer content preserved.

---

## summarize

* Immutable session created.
* Current context updated.

---

## doctor

* Repository validated.
* Problems reported.
* Correct exit code returned.

---

# Extensibility

Future extensions include:

* language analyzers
* framework analyzers
* custom artifact types
* custom merge strategies
* custom validators

The core engine should not require modification to support these.

---

# Success Criteria

DoozCTL succeeds when:

* Any repository can be initialized in under one minute.
* Repository standards can be installed without modification.
* Organizations can maintain their own Standards Packages independently.
* Switching AI coding assistants requires no repository redesign.
* Repository knowledge persists independently of AI conversations.

---

# Guiding Principle

> **Persist only the minimum knowledge required for the next engineer or AI agent to continue successfully.**

The engine manages artifacts.

The Standards Package defines behavior.

The repository owns the knowledge.
