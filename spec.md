# DoozCTL Specification

**Version:** 2.0 Draft
**Status:** Canonical

---

# Vision

DoozCTL is a lightweight, vendor-neutral CLI that installs and maintains AI repository standards.

It does **not** define engineering practices.

It provides the engine that renders, installs, updates and validates repository artifacts supplied by an external Standards Package.

The repository becomes the long-term memory.

AI coding assistants become interchangeable execution engines.

---

# Philosophy

* Minimal context.
* Minimal configuration.
* Repository over conversation.
* Behavior over documentation.
* Facts over prose.
* Deterministic over magical.
* Brownfield first.
* Offline first.
* Vendor neutral.

---

# Non Goals

DoozCTL is **not**:

* an AI coding assistant
* an engineering standard
* a coding guideline
* a documentation generator
* a build system
* a package manager
* a deployment framework

---

# Core Principle

> **DoozCTL is a rendering engine for repository standards, not the author of those standards.**

Everything repository-specific comes from an external Standards Package.

# Standards Package

A Standards Package is an external dependency.

Its internal structure, artifacts and contents are outside the scope of DoozCTL.

The engine interacts only through a published contract.

The engine must not assume or require any specific artifact names, repository layout or engineering standard.

## Package Layout

A Standards Package is a plain directory. No packaging format, registry or plugin system.

```text
standards/
    package.json
    artifacts/
    schemas/
```

The engine loads a package only through its manifest. It never scans directories, invents artifacts, or interprets package internals.

## Manifest Schema

```json
{
  "format": 1,
  "name": "@dooziesoft/standards",
  "version": "1.0.0",
  "engine": ">=1.0.0",
  "artifacts": [
    {
      "id": "agents",
      "source": "artifacts/AGENTS.md",
      "destination": "AGENTS.md",
      "merge": "managed-blocks"
    }
  ]
}
```

* `format` — package structure version, used by the loader. Unsupported formats are rejected.
* `name` — package name.
* `version` — version of the standards package itself.
* `engine` — required engine version range. Metadata only; not enforced.
* `artifacts` — artifact declarations.

## Format Versioning

`format` and `version` are independent:

* `format` evolves when the package structure changes.
* `version` identifies the standards content.

This lets the package format evolve without re-versioning the standards content, and vice versa.

## Validation

The loader validates only:

* package exists
* JSON is valid
* artifact source file exists
* merge strategy is valid

Nothing else.

## Non-Features

The package format has no:

* inheritance, includes, imports or dependencies
* conditions, expressions or loops
* plugin hooks or code
* YAML, TOML, or custom template syntax

Every one of those would make the project worse. Add them only in a future format version, not today.

# Artifact Model

Everything generated by DoozCTL is an Artifact.

## Artifact Declaration

An artifact declaration in the manifest is minimal metadata:

```json
{
  "id": "agents",
  "source": "artifacts/AGENTS.md",
  "destination": "AGENTS.md",
  "merge": "managed-blocks"
}
```

* `id` — stable identifier.
* `source` — path to the artifact file inside the package.
* `destination` — path inside the repository.
* `merge` — merge strategy.

Declarations carry no templates, variables, or conditions.

## Artifact

Every artifact has:

* source
* destination
* merge strategy
* optional schema

The engine treats every artifact identically.

It does not special-case AGENTS.md.

# Variables

Repository analysis becomes variables available during rendering.

Variables are hierarchical namespaces:

```yaml
analysis:
  language:
  framework:
  tests:

repository:
  root:
  git:
  statistics:
  aiFiles:

build:
  buildSystem:
  packageManager:
  ci:
  docker:
```

Variable syntax is Mustache:

```text
{{analysis.language}}

{{repository.root}}

{{build.packageManager}}
```

Artifacts may reference these variables.

## Rendering

Rendering is the Mustache subset above and nothing else.

* `{{dotted.path}}` placeholders are substituted against the variables.
* Missing variables render as empty strings.
* Values are rendered unescaped plain text (artifacts are Markdown, not HTML).
* Arrays are comma-joined.
* Output is UTF-8, normalized to LF line endings.
* Rendering is deterministic: identical template and variables produce identical output.

No helpers, functions, conditions, expressions, partials, includes, or scripting. Any `{{...}}` that is not a resolvable variable renders as an empty string.

# Merge Strategies

The engine supports multiple merge strategies.

## Managed Blocks

Update managed sections only.

Preserve everything else.

---

## Replace Generated

Replace previously generated files.

---

## Overwrite

Replace entire artifact.

Used for generated state.

---

## Append

Create new immutable artifacts.

Used for session summaries.

# Generated State

DoozCTL maintains:

```text
.dooz/

manifest.json

.ai/

current-context.md

repository-analysis.json

sessions/
```

`.dooz/` holds engine state. `.ai/` holds AI-readable memory. These files belong to the engine. They are regenerated as required.

---

# Wrapper Files

Wrapper files are supplied by the Standards Package.

Typical wrapper:

```text
Read AGENTS.md before taking any action.

This file is generated.
```

The engine does not define wrapper contents.

---

# Constraints

The engine must be:

* deterministic
* offline capable
* cross-platform
* modular
* testable
* vendor neutral

It must never:

* overwrite unmanaged content
* fabricate repository information
* modify application code during analysis
* depend on internet connectivity
* embed company-specific guidance

# Extensibility

Future extensions include:

* language analyzers
* framework analyzers
* custom artifact types
* custom merge strategies
* custom validators

The core engine should not require modification to support these.

---

# Success Criteria

DoozCTL succeeds when:

* Any repository can be initialized in under one minute.
* Repository standards can be installed without modification.
* Organizations can maintain their own Standards Packages independently.
* Switching AI coding assistants requires no repository redesign.
* Repository knowledge persists independently of AI conversations.

---

# Guiding Principle

> **Persist only the minimum knowledge required for the next engineer or AI agent to continue successfully.**

The engine manages artifacts.

The Standards Package defines behavior.

The repository owns the knowledge.
