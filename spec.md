# DoozCTL Specification

**Version:** 2.0 Draft
**Status:** Canonical

---

# Vision

DoozCTL is a lightweight, vendor-neutral CLI that installs and maintains AI repository standards.

It does **not** define engineering practices.

It provides the engine that renders, installs, updates and validates repository artifacts supplied by an external Standards Package.

The repository becomes the long-term memory.

AI coding assistants become interchangeable execution engines.

---

# Philosophy

* Minimal context.
* Minimal configuration.
* Repository over conversation.
* Behavior over documentation.
* Facts over prose.
* Deterministic over magical.
* Brownfield first.
* Offline first.
* Vendor neutral.
* Prefer preserving user-authored content over propagating generated content.

---

# Non Goals

DoozCTL is **not**:

* an AI coding assistant
* an engineering standard
* a coding guideline
* a documentation generator
* a build system
* a package manager
* a deployment framework

---

# Core Principle

> **DoozCTL is a rendering engine for repository standards, not the author of those standards.**

Everything repository-specific comes from an external Standards Package.

---

# Standards Package

A Standards Package is an external dependency.

Its internal structure, artifacts and contents are outside the scope of DoozCTL.

The engine interacts only through a published contract.

The engine must not assume or require any specific artifact names, repository layout or engineering standard.

## Package Layout

A Standards Package is a plain directory. No packaging format, registry or plugin system.

```text
standards/
    package.json
    artifacts/
    schemas/
```

The engine loads a package only through its manifest. It never scans directories, invents artifacts, or interprets package internals.

## Manifest Schema

```json
{
  "format": 2,
  "name": "@dooziesoft/standards",
  "version": "1.0.0",
  "engine": ">=1.0.0",
  "artifacts": [
    {
      "id": "agents",
      "source": "artifacts/AGENTS.md",
      "destination": "AGENTS.md",
      "merge": "managed-blocks",
      "lifecycle": ["init", "sync"]
    }
  ]
}
```

* `format` — package structure version, used by the loader. Unsupported formats are rejected. Format 2 introduces the artifact lifecycle.
* `name` — package name.
* `version` — version of the standards package itself.
* `engine` — required engine version range. Metadata only; not enforced.
* `artifacts` — artifact declarations.

## Format Versioning

`format` and `version` are independent:

* `format` evolves when the package structure changes.
* `version` identifies the standards content.

This lets the package format evolve without re-versioning the standards content, and vice versa.

## Validation

The loader validates only:

* package exists
* JSON is valid
* artifact source file exists
* merge strategy is valid
* artifact lifecycle is valid (required, non-empty, values from `init`, `sync`, `summarize`)

Nothing else.

## Non-Features

The package format has no:

* inheritance, includes, imports or dependencies
* conditions, expressions or loops
* plugin hooks or code
* YAML, TOML, or custom template syntax

Every one of those would make the project worse. Add them only in a future format version, not today.

# Artifact Model

Everything generated by DoozCTL is an Artifact.

## Artifact Declaration

An artifact declaration in the manifest is minimal metadata:

```json
{
  "id": "agents",
  "source": "artifacts/AGENTS.md",
  "destination": "AGENTS.md",
  "merge": "managed-blocks",
  "lifecycle": ["init", "sync"]
}
```

* `id` — stable identifier.
* `source` — path to the artifact file inside the package.
* `destination` — path inside the repository.
* `merge` — merge strategy.
* `lifecycle` — the workflows that process this artifact.

Declarations carry no templates, variables, or conditions.

## Lifecycle

An artifact participates only in the workflows its `lifecycle` names:

| Workflow     | Processes artifacts with lifecycle |
| ------------ | ---------------------------------- |
| `init`       | `init`                             |
| `sync`       | `sync`                             |
| `summarize`  | `summarize`                        |

Artifacts outside a workflow's lifecycle are invisible to it: they are not loaded, rendered, merged or written by that workflow, and are skipped with a report. Merge describes how content combines; lifecycle describes when.

This keeps `sync` unconditionally idempotent: append-only session artifacts declare `["summarize"]`, so neither `init` nor `sync` ever executes `append`.

## Artifact

Every artifact has:

* source
* destination
* merge strategy
* lifecycle
* optional schema

The engine treats every artifact identically.

It does not special-case AGENTS.md.

# Variables

Repository analysis becomes variables available during rendering.

Variables are hierarchical namespaces:

```yaml
analysis:
  language:
  framework:
  tests:

repository:
  root:
  git:
  statistics:
  aiFiles:

build:
  buildSystem:
  packageManager:
  ci:
  docker:
```

Variable syntax is Mustache:

```text
{{analysis.language}}

{{repository.root}}

{{build.packageManager}}
```

Artifacts may reference these variables.

## Rendering

Rendering is the Mustache subset above and nothing else.

* `{{dotted.path}}` placeholders are substituted against the variables.
* Missing variables render as empty strings.
* Values are rendered unescaped plain text (artifacts are Markdown, not HTML).
* Arrays are comma-joined.
* Output is UTF-8, normalized to LF line endings.
* Rendering is deterministic: identical template and variables produce identical output.

No helpers, functions, conditions, expressions, partials, includes, or scripting. Any `{{...}}` that is not a resolvable variable renders as an empty string.

# Merge Strategies

The engine merges a rendered artifact into the repository using exactly one of four strategies.

The merge engine knows only text. It does not know AGENTS.md, Markdown, JSON, Current Context, Sessions, or Templates.

```text
Existing File

+

Rendered Artifact

+

Merge Strategy

↓

Merged Output
```

## Merge Rules

* If the destination file does not exist, the engine writes the rendered artifact directly. Merge applies only to files that already exist.
* Never write unless the merge succeeds.
* Never partially update.
* No merge conflicts, no three-way merge, no Git logic. If a merge is impossible, return an error and leave the file untouched. The user decides.
* Determinism: identical input produces identical output, always.

## overwrite

Replace the existing content completely.

Used for generated machine state.

Example:

```text
.dooz/manifest.json
```

## append

Append the rendered artifact to the existing content.

Never modify previous content.

Used for immutable session files. Append artifacts declare lifecycle `["summarize"]`; `init` and `sync` never execute `append`.

Example:

```text
.ai/sessions/
```

## replace-generated

Replace the existing file only if it was previously generated by the engine.

Otherwise fail safely.

Never overwrite a user-created file accidentally.

Used for wrapper files.

## managed-blocks

Update only the content inside managed blocks.

Everything outside the managed blocks remains untouched.

Managed-blocks never propagates surrounding boilerplate. Content outside the managed regions is intentionally preserved; boilerplate updates require `replace-generated` or manual edits.

### Managed Block Markers

Frozen forever. No alternatives.

```text
<!-- DOOZCTL:BEGIN:v1 section-name -->
<!-- DOOZCTL:END:v1 section-name -->
```

Example:

```markdown
# AGENTS

User notes...

<!-- DOOZCTL:BEGIN:v1 repository-analysis -->

generated content

<!-- DOOZCTL:END:v1 repository-analysis -->

User notes...
```

Only the region between matching markers may change.

### Managed Block Rules

The engine fails (returns an error, writes nothing) on:

* missing markers
* BEGIN without a matching END
* duplicate section names
* nested markers
* unknown merge strategy

Never guess. Never repair malformed files.

Whitespace outside a block is preserved exactly.

Whitespace inside a block is replaced exactly.

# Commands

## init

Responsibilities

* Detect repository
* Analyze repository
* Load Standards Package
* Render artifacts
* Merge existing files
* Write generated artifacts
* Create manifest

---

## analyze

Update repository analysis (`.ai/repository-analysis.json`).

Requires an initialized repository.

---

## sync

Re-render the artifacts in the sync lifecycle.

Preserve developer content.

Skip artifacts outside the sync lifecycle and report them.

---

## doctor

Validate repository.

Check:

* artifacts
* manifest
* managed blocks
* schemas

---

## summarize

Create new session summary.

Update current context.

---

## status

Display repository status.

# Generated State

DoozCTL maintains:

```text
.dooz/

manifest.json

.ai/

current-context.md

repository-analysis.json

sessions/
```

`.dooz/` holds engine state. `.ai/` holds AI-readable memory. These files belong to the engine. They are regenerated as required.

---

# Wrapper Files

Wrapper files are supplied by the Standards Package.

Typical wrapper:

```text
Read AGENTS.md before taking any action.

This file is generated.
```

The engine does not define wrapper contents.

# Constraints

The engine must be:

* deterministic
* offline capable
* cross-platform
* modular
* testable
* vendor neutral

It must never:

* overwrite unmanaged content
* fabricate repository information
* modify application code during analysis
* depend on internet connectivity
* embed company-specific guidance

# Extensibility

Future extensions include:

* language analyzers
* framework analyzers
* custom artifact types
* custom merge strategies
* custom validators

The core engine should not require modification to support these.

---

# Success Criteria

DoozCTL succeeds when:

* Any repository can be initialized in under one minute.
* Repository standards can be installed without modification.
* Organizations can maintain their own Standards Packages independently.
* Switching AI coding assistants requires no repository redesign.
* Repository knowledge persists independently of AI conversations.

---

# Guiding Principle

> **Persist only the minimum knowledge required for the next engineer or AI agent to continue successfully.**

The engine manages artifacts.

The Standards Package defines behavior.

The repository owns the knowledge.
